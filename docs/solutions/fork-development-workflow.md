# Fork 开发与上游同步规范

本项目基于自己的 fork 持续开发，定期合并上游更新。自有功能通过验证即可发布，不等待上游接受所有 PR。上游未接受的功能由本项目继续维护。

## 仓库和分支职责

- `origin`：`iqiuzixuan/axonhub`，保存本项目的代码。
- `upstream`：`looplj/axonhub`，提供上游更新；当前跟随 `unstable`。
- 开始工作前重新检查远程地址和工作区状态，不把本文记录当成远端实时状态。

| 分支 | 职责 | 起点和去向 |
| --- | --- | --- |
| `unstable` | 上游原版镜像，不放自有改动 | 从 `upstream/unstable` 快进更新 |
| `develop` | 长期维护主线，包含已验证自有功能；提供部署来源 | 接收功能及上游同步分支 |
| `feat/*`、`fix/*` | 一个独立功能或修复 | 从 `develop` 创建，验证后合回 |
| `docs/*`、`chore/*` | 文档或开发配置 | 从 `develop` 创建，核验后合回 |
| `sync/upstream-YYYYMMDD` | 上游更新集成和冲突处理 | 从 `develop` 创建，合入上游，验证后合回 |
| `pr/*` | 单独向上游贡献 | 从上游目标分支创建，只带该需求改动 |

功能分支和同步分支均为临时分支；改动合入 `develop` 后，删除其分支名不会删除已合入的提交。现阶段无需增加长期 release 分支。

## 开始开发

1. 检查 `git status`、当前分支、未暂存与暂存差异，以及最近提交。保留其他任务的改动。
2. 确认本地 `develop` 与 `origin/develop` 的关系。远端尚无 `develop` 时，首次发布经用户授权后执行 `git push -u origin develop`；以后跟踪 `origin/develop`，不跟踪 `upstream/unstable`。
3. 明确从 `develop` 创建功能分支，例如 `git switch -c feat/user-display-name develop`。不要从当前功能分支随手创建无关功能。
4. 完成代码、接口、数据迁移、文案和相关测试。不同目的分开提交，提交信息遵循仓库中文规范。
5. 检查分支差异只包含本需求，验证通过后使用普通合并（建议 `--no-ff`）合回 `develop`，记录功能提交和合并提交。
6. 若验证期间 `develop` 又有更新，先合入最新主线并验证受影响部分。未通过检查的分支不进入部署主线。

同一 checkout 不同时运行互相切换分支的开发任务；并行任务需要独立 worktree。

## 合并上游

推荐每周评估更新，关键修复及时处理；无需每个上游提交都立即部署。

1. `git fetch upstream` 获取真实上游状态，不强制覆盖本地或 fork 的 tag。
2. 从最新 `develop` 建立 `sync/upstream-YYYYMMDD`。
3. 在同步分支执行 `git merge --no-ff upstream/unstable`。没有新提交时记录“已同步”，不要制造空合并。
4. 逐项解决冲突，结合双方意图保留功能；不能整批选择 ours/theirs 来代替分析。
5. 若冲突涉及 Ent/GraphQL，先合并 schema 源文件，再运行 `make generate`。同时检查手写查询、迁移和前端读写链路。
6. 验证相关上游行为、自有功能和旧数据库升级路径。没有 Git 文字冲突不等于没有行为冲突。
7. 验证通过后合回 `develop`，再按部署流程发布。失败时保持 `develop` 不变，继续修复或中止同步。

使用 merge 保留上游和本地共同历史，避免每次升级重新搬运所有自有补丁。不要对已发布 `develop` 执行重置到上游、强制同步或重写历史的 rebase。

`origin/unstable` 可以单独快进同步为上游镜像。更新它不等于已经更新 `develop`，也不会自动带上自有功能。

## 上游 PR 独立推进

不要直接以 `develop` 向上游提 PR，因为它可能包含多个自有需求。

需要贡献时，从最新上游目标分支建立 `pr/需求名称`，使用 cherry-pick 挑选该需求的提交，检查最终差异并验证。若原功能依赖其他 fork 改动，需要移除依赖或拆清贡献范围。

| 上游处理结果 | 本项目处理 |
| --- | --- |
| 未提交、审核中、拒绝 | 自有功能留在 `develop`，继续同步和维护 |
| 原样接受 | 后续正常合并上游，核对最终代码，避免重复应用 |
| 压缩或改写提交后接受 | 不按提交哈希判断功能是否缺失，比较实际行为和最终差异 |
| 上游提供另一种实现 | 在同步分支协调两种实现，保留必要兼容后逐步收敛 |

已经上线的数据迁移必须保持连续。不能因为上游接受了另一套字段设计，就直接回退或删除自己的迁移。

## 持续检查和部署

- 构建、测试及已有 lint 工作流应覆盖推送到 `develop` 和目标为 `develop` 的 PR。注意 `development` 和 `develop` 是不同分支。
- 沿用仓库命令限制：未明确要求时不在本地运行 lint/build，也不重启已托管的开发服务器；执行与改动直接相关的测试。
- fork 的镜像发布流程必须使用自有源码分支和自有镜像仓库。上游附带的 unstable 发布流程不等于自有 develop 发布流程。
- 每次部署固定并记录经过验证的 commit SHA 和镜像 digest；可添加自有命名的 tag，避免误触上游 `v*` 发布流程。
- 合并 `develop` 不自动授权部署。应用含数据库迁移时，回滚方案必须同时考虑数据库；不能把切回旧镜像视为完整回滚。
- 远程 push 和生产部署按用户授权执行。仅本地完成时明确报告尚未推送或部署，不声称远端已同步。

## 验证分支流程

真实需求应验证：从正确主线建分支、需求提交边界清晰、相关测试通过、合并后两边历史均保留、工作区干净。

上游暂时没有新提交时，可在 `/tmp` 的隔离仓库中演练：保留未被上游接受的功能、合入模拟上游更新、解决同文件冲突、向本地模拟 fork 推送、提取干净的上游贡献。模拟提交不得进入真实 `develop`，报告须区分真实合并和模拟验证。
